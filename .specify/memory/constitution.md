# PDF RAG 知识库系统项目宪章

## 核心原则

### 一、阶段边界交付

项目必须一次只实现一个已声明阶段；未经明确修改项目规格说明，不得把 V2/V3
能力带入 V1。每个阶段必须有可演示的验收结果、记录完整的运行命令和简短的未完成
事项列表，以保持学习路径和评审范围清晰。

### 二、RAG 模块单一职责

PDF 解析、父子分块、嵌入、向量索引、检索、父级加载、上下文构建、生成、评估、
日志和 API 传输必须保持职责分离，并拥有稳定契约。流水线可以协调这些服务，但
不得吸收它们的实现细节。这样可以保持模块可替换，并使 RAG 数据流易于理解。

### 三、基于证据回答

助手必须只根据检索到的知识库上下文回答，并在上下文不足时明确说明。每个展示的
答案都必须在可用时暴露来源文档和检索证据。评估可以给答案打分，但低分不得在 V1
触发没有计划的第二次检索，从而避免无依据陈述并保持 V1 行为确定。

### 四、安全且一致的数据处理

密钥必须来自环境配置，不得提交或硬编码。密码必须以哈希形式保存。文档清单、PDF
文件、Markdown 文件、父级记录、子级元数据和向量索引在上传、处理失败和删除后必须
保持一致。必要的破坏性操作必须重建派生索引，不能留下过期检索状态。

### 五、可观察且可验证的行为

每个 RAG 请求必须获得一个请求标识，并由结构化日志和流式事件共享。重要流水线步骤
必须报告状态、耗时和相关详情，同时不能泄露密钥。新增行为必须包含针对性测试；在
一个阶段可以完成前，API 契约、解析/分块边界、索引一致性、身份认证和端到端 RAG
流程必须具有集成覆盖。优先保持简单，避免推测性抽象。

## 产品边界

V1 是一个单管理员、文本型 PDF、单轮问答的知识库系统。包含 PDF 上传、Markdown
提取、父子分块、嵌入和 FAISS 检索、父级上下文构建、OpenAI 兼容模型生成、结构化
答案评估、JWT 登录、SSE 进度事件和请求级 JSONL 日志。OCR、图像理解、联网搜索、
多用户角色、多轮记忆、查询改写、混合检索、代理循环、外部向量数据库和部署打包，
在后续批准新的规格说明前都不属于范围。

## 交付流程

项目必须使用 Spec Kit 产物作为事实来源：宪章、功能规格、计划、检查清单、任务、
分析、实现和收敛复核。所有变更必须针对当前功能目录进行规划。实现前，需求必须
可测试，范围必须受控，已知歧义必须解决或明确记录。实现后，必须运行阶段验收检查
和相关自动化测试，最终报告必须列出变更文件、启动命令、测试和未完成工作。

## 治理

当实现细节与已批准的功能规格冲突时，本宪章具有约束力。宪章修订必须通过宪章流程，
包含同步影响说明，更新语义版本，并解释原因。重大版本会删除或重新定义原则；次要
版本会增加或实质扩展原则或治理章节；补丁版本只澄清文字而不改变项目义务。每个实现
计划、复核和阶段交接都必须检查是否符合本文件。复杂度或范围扩展必须在相关 Spec Kit
产物中说明理由。
