## 1. 交付结论

Q3 现在按第 3 页的详细原文展示完整流程，不再用第 4 页简表的三步回答替代。五题本次均有来源，Q1、Q2、Q4、Q5 的关键事实及限定条件未回退。每题仍为 2 次本机模型调用，云端和 Judge 调用为 0。

这不是“给模型补一句提示词就宣布修复”：生成器要求模型选择已经核对来源的完整段落编号，程序从保留原文生成流程正文与引用。模型的简短操作回答不作为最终指导；未知编号、截断正文、缺失完整单元、冲突或跨文档拼接会安全降级。

这里的“完整单元”指结构上保留的原文段落，不等于已经证明它包含该问题的所有必要操作。首次模型仍可能误判意图，生成模型也可能选择错误段落；这些风险没有被本次五题验收消除。

## 2. 当前实际处理链路

1. 沿用现有第一次模型分析，输出 `requires_procedure`；判断操作、恢复、解除故障等意图，没有新增按提问关键词或正则猜流程的入口。缺少该字段的旧输出按保守流程模式处理，明确 `false` 才走普通事实回答。
2. Agent 沿用 Child 检索与 Parent Store 读取。流程证据选择器另外只读已有 Markdown，要求整个章节去掉版面空白后与 Parent 一致，再恢复原文段落、断行及有序列表。缺失、过大、过期或不匹配的派生文件不触发 PDF 重解析。
3. 流程排序优先考虑完整叙述单元与问题的相关性，保留段落内前提及后续动作，不将表格行当作完整流程。单流程输入只发送完整叙述单元，去除 Parent 与段落的重复文本；完整 Parent 另留审计字段。
4. 生成模型在原有第二次调用中返回 `procedure_unit_ids`，例如 `E1.P3`。生成器再次检查该单元确实存在于保留正文及实际上下文，然后按来源页码、Parent 顺序和段落顺序展示原文。单流程不会再附上简表缩写；多问题场景可以保留另有依据的事实引文。
5. 原数值、引文、冲突校验与预算保持。没有新加第三次模型或默认 Judge；评估仍显示 `completeness_status=not_evaluated`，不恢复固定高分。

Parent 工具本身仍只读 Parent Store。上述 Markdown 读取发生在证据选择层，不是 Parent 工具重新解析 PDF。结构识别使用 Markdown 标题、列表等正则；既有数值/型号字面校验也仍在，但没有把测试设备或“断开负载”等动作写成通用业务意图规则。

主要实现：[原文结构恢复](../../backend/app/rag/procedure_evidence.py)、[证据选择](../../backend/app/rag/evidence.py)、[分析与契约](../../backend/app/rag/query_analysis.py)、[生成校验](../../backend/app/rag/generator.py)。字段经过 `model_schema.py`、`graph_state.py`、`graph.py`、`nodes.py` 传递。

> 如果故障代码为 OC-16，表示发生过流保护。应先断开负载，等待设备完全放电，再检查负载端是否短 路。确认负载正常后，按确认键清除告警，最后重新执行上电流程。

“短 路”等空白来自 PDF 提取；没有猜测或替换操作步骤。Q1 被本机模型保守标为流程，因此展示了包括后续启动动作和警示在内的完整原文，答案比单纯检查清单更长，这是保留完整单元的取舍，不宣称回答长度已最优。

本代理对照保留原文核对了上述答案与条件；脚本仅做固定题目的字面定位和调用/来源检查，不是语义 Judge 或 RAGAS 评分，没有把题集标为已人工审核。
