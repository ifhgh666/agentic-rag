## 1. 依据与当前事实

参考的是 [agentic-rag-for-dummies](https://github.com/GiovanniPasq/agentic-rag-for-dummies) 的真实实现，而不是只参照其架构图：

- [主图 `graph.py`](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/project/rag_agent/graph.py) 以 `summarize_history → rewrite_query` 进入问答；澄清使用图检查点和 `interrupt_before`。
- [节点 `nodes.py`](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/project/rag_agent/nodes.py) 将摘要、近期普通消息、未解决问题和补充信息送给结构化模型；澄清消息被标记为内部消息，不当作普通问答历史。
- [状态 `graph_state.py`](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/project/rag_agent/graph_state.py) 显式区分 `conversation_summary`、`pendingQuery`、`pendingClarifications` 和 `rewrittenQuestions`。
- [评估 Notebook](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/notebooks/evaluation.ipynb) 对精选问答集离线运行 RAGAS；使用独立 Judge 模型，分别记录 AnswerAccuracy、ContextRelevance、ResponseGroundedness、ContextPrecision、ContextRecall。它**不是**每次在线回答都给用户打一个可信度分数。

| 方面 | 我们当前实现 | 造成的问题 | 本方案取舍 |
|---|---|---|---|
| 问题理解 | `conversation_memory.py` 用代词正则判断是否需要历史；`query_analysis.py` 用长度、连接词和指代正则决定是否跳过模型；特定“型号＋并列问题”还有规则兜底 | 同义词、陌生说法、混合意图容易误判；用例越多，补丁越多 | **模型优先**做一次结构化问题理解；正则只留给型号/数值格式校验等确定性任务 |
| 待澄清状态 | `ConversationMemory._threads` 另存 `pending` 字符串；下一条非空消息直接拼成“原问题＋补充信息”，并假定已清晰 | 用户改问新题也可能被误当补充；澄清轮次与正常消息混杂；进程重启丢失 | 在统一的线程状态中显式保存待澄清问题、补充记录与状态转移；模型判断补充、新题或仍不清楚，用户可显式选择 |

| 在线评分 | `evaluator.py` 对非空回答给忠实性 90、完整性 78 等固定值；前端 `ScoreCard` 显示“总体可信度” | Q3 漏掉安全前置步骤，仍显示 84/100 | 在线只展示确实核验过的信号；正确性/完整性移到有标准答案的离线评估，不再展示伪精确分数 |

## 2. 目标链路与关键决策

```text
新消息 + thread_id
  → 读取线程状态（近期普通对话、摘要、待澄清事项）
  → 一次结构化本地模型分析（是否新题／补充；是否清晰；独立检索问题 ≤ 3）
  ├─ 仍不清晰：保存待澄清状态 → 问一个具体问题 → 暂停问答
  └─ 已清晰：清除或切换待澄清状态 → 现有 Child/Parent 检索与生成链路
                  → 可核验的在线状态 + 引文 → 按阈值更新摘要
离线：固定题集 + 实际答案/检索上下文 + 独立 Judge → 分项评估报告
```

### 2.1 问题理解：模型负责语义，程序负责边界

1. 在 Ollama 可用时，**每条新用户消息只做一次**结构化分析，统一完成指代消解、多问题拆解和澄清判断；不另设“先用一个模型决定要不要调用另一个模型”的阶段。输入为当前原文、有限的近期普通对话、可用摘要，以及待澄清状态；不把整段 PDF 或工具日志送入分析器。
2. 输出契约至少包含：消息关系（新题／补充／不确定）、`is_clear`、最多 3 个独立检索问题、单个 `clarification_needed`。校验型号、数值、限定条件是否被保留；禁止模型补出原问题和历史中不存在的设备信息。简单独立问题可原样输出，不强迫改写。
3. 删除正则驱动的语义分流、默认“含代词即追问”以及为通过个别案例而加的语义特例。仍可用正则识别格式合法性、精确型号和引文数值；这类检查不决定用户意图。
4. 模型超时、无效 JSON 或预算耗尽时，不把“未能判断”伪装成 `is_clear=true`。可安全原样检索的输入只以原文检索；有待澄清状态或明显无法确定指代时提示用户重新表述/选择新题，不擅自拼接历史。失败须记录原因和降级路径。
5. 沿用 `thread_id + 当前问题 + 历史状态指纹 + index_version` 缓存，并记录命中、分析 Token、耗时。模型调用预算必须包括本次分析和摘要；复杂拆题不得突破现有全请求上限。代价预期是简单题从目前常见的 1 次调用增加到约 2 次，实际值以阶段 A/B 实测为准，若本地 4B 模型延迟或误判不可接受，再评估更小的专用分析模型或经过验证的**非语义**快速路径，不先恢复大量正则补丁。

### 2.2 待澄清与记忆：一份状态、一套转移

建议线程状态：`recent_messages`（只含普通用户/助手轮次）、`conversation_summary`、`pending_query`、`pending_clarifications`、`phase`（空闲／待澄清／回答中）、`state_version`。请求级的工具消息、检索上下文和模型内部分析单独存放，不混入用户对话记忆。现有 `graph_state.py` 的 `pending_query` 初始化后未参与真实待澄清流程，应与 `ConversationMemory._threads` 合并为一个事实来源；若采用 LangGraph checkpoint，须确保 API 按相同 `thread_id` 恢复、写入原子化，并防止同线程并发请求互相覆盖。

状态转移约定：

| 旧状态 | 用户输入 | 判定／动作 | 新状态 |
|---|---|---|---|
| 空闲 | 独立且清楚的问题 | 分析、检索、回答 | 空闲；完成轮次进入近期消息 |
| 空闲 | 对象/条件未说明 | 保存原始问题，发出具体澄清 | 待澄清；**不**把占位回答写成正常问答 |
| 待澄清 | 补充信息 | 累积补充，重新分析原问题；充分时检索 | 仍待澄清或空闲 |
| 待澄清 | 明确提出新问题 | 先清除或归档旧待办，再分析新题；不得拼接 | 空闲或新的待澄清 |
| 待澄清 | 表述仍无法判别 | 请用户选择“继续补充／开始新问题／取消” | 待澄清 |
| 待澄清 | 用户明确取消 | 清除待办，不生成旧题答案 | 空闲 |

参考项目的显式 `pendingQuery/pendingClarifications` 和中断点值得借鉴，但它也默认中断后的下一条输入用于澄清；我们要额外处理**用户中途换题**。前端可提供明确操作，文本入口仍由同一次结构化分析判别；不根据 `role=user` 或下一条消息非空就自动视为补充。

摘要只在普通对话超过配置的消息/Token 窗口时触发；对旧摘要与溢出轮次做增量概括，限制长度，并验证型号、数值、用户偏好及未解决事项没有无依据增加或明显丢失。摘要是问题理解的背景，不是可引用的 PDF 证据。第一阶段可继续进程内 checkpoint，并在界面说明重启会丢失会话；持久化到 SQLite 是后续独立决策，不在本方案中暗中引入。

### 2.3 评估：在线证据状态与离线质量测量分开

1. 在线保留能被程序证明的状态：是否找到检索上下文、引文是否能映射到实际片段、数值是否有明确证据、回答是否走“证据不足”分支；对流程完整性、事实正确性等**未验证项**标为“未评估”，不计算“总体可信度”。引文有效也不等于整段回答正确。
2. `EvaluationResult` 当前后端和前端均要求 0–100 数值，`ScoreCard` 直接显示。实施时先定义新的版本化响应/SSE 契约与兼容迁移：旧字段过渡期不能继续承载虚构分数；前端改为“已核验／未核验／存在问题＋原因”，接口测试覆盖旧消费者。不要简单把固定 84 改成固定 90。
3. 建立带来源页和人工标准答案的离线题集，先纳入 Q1–Q5，再补充同义改写、跨轮指代、并列问题、澄清后继续、待澄清时换题、无证据、数值冲突、操作步骤遗漏。Q3 必须包含“断开负载→等待完全放电→检查无短路→清除告警→重新上电”的安全步骤核对；业务逻辑不得硬编码这份测试 PDF。
4. 仿照参考项目的 Notebook，用**实际生成答案和实际送入生成器的上下文**运行独立离线 Judge，分别输出 AnswerAccuracy、ContextRelevance、ResponseGroundedness、ContextPrecision、ContextRecall；保留每题原始结果、均值、版本、模型和人工复核结论。标准答案和 Judge 自身也可能有误，特别是安全步骤，人工验收仍是最终关卡。
5. 默认**不**在每次在线问答后增加 Judge 调用。若需要下载第二个本地 Judge 模型或调整硬件资源，先单独征得同意；云端调用维持为 0。离线评估不作为回答时的“实时评分”。

## 3. 分阶段交付与验收

本方案是 [既有后续计划](v3-post-acceptance-plan.md) 的**专项细化**，不另起一套相互竞争的 V3 编号。执行前应把下列阶段与原 V3-6～V3-8 及对应 Spec Kit `spec.md/plan.md/tasks.md` 对齐；旧计划中的 Q3 证据与生成修复仍有效，不因本文件被跳过。此次只写设计，未修改已完成的 V3-0～V3-5 记录。

| 阶段 | 工作内容 | 交付物 | 阶段通过条件 |
|---|---|---|---|
| A：基线与契约 | 固定现有误判和 Q3 示例；建立状态转移、结构化分析输出、在线评估响应契约；记录当前模型调用/Token/耗时 | 设计契约、可复现题集、基线报告；同步 Spec Kit 产物 | 能复现正则误判、换题被拼接、漏步骤仍获高分；每个案例有预期行为 |
| B：问题理解与待澄清 | 单次模型优先分析；统一线程状态；区分普通/内部消息；补充、新题、取消和异常降级；按阈值摘要 | 后端改动、必要的前端待澄清操作、单元/集成测试、阶段报告 | 同义追问与并列问题正确；换题不污染旧待办；线程隔离；摘要不被当作 PDF 证据；调用上限可审计 |
| C：可信评估 | 移除固定高分展示；在线改可核验状态；构建离线题集和 Judge 流程；对照人工标注 | API/SSE/前端迁移、评估脚本/题集、逐题报告 | Q3 缺步骤不能显示“完整/可信”；无证据不获虚高分；五项离线指标能重跑，原始数据可追溯 |
| D：正式库回归 | 对原五题和新增多轮/异常题按相同索引复测；Q3 至少重复 3 次；比较质量与成本 | 正式库验收、回归测试、Token/耗时对比、遗留问题清单 | Q1–Q5 不退化，Q3 安全步骤齐全且有来源；待澄清场景符合契约；没有未批准的云端调用或索引变更 |

每阶段完成后**暂停并汇报**，不自动执行下一阶段。数值型 RAGAS 阈值须在阶段 A 的人工标注和 Judge 稳定性校准后设定，不能为“通过验收”倒推阈值。阶段 B 增加一次入口模型分析有明确性能成本；报告必须同时给出每题调用次数、实测与估算 Token、延迟，并与 V3-5 的 9,377 Token/225 秒基线比较。若成本不可接受，暂停讨论折中方案，而非悄悄恢复正则语义路由。

## 4. 边界、风险与下一步

- 不照搬参考项目的所有 Agent 调用、8B 模型或在线 Judge：本机当前使用 Ollama 小模型，模型优先方案需要先测稳定性与延迟。
- 不导入/删除/重建正式知识库，不改密钥、密码和模型配置；业务 PDF 试点仍按既有计划另行确认。
- 不把离线 RAGAS 分数宣传为单条在线回答的真实正确率；对操作安全类问题以完整证据和人工复核为准。
- 项目宪章要求阶段交付、模块分工、可引用证据、接口测试和 Spec Kit 事实来源。本文件作为讨论稿；进入实施前先同步当前功能的规格与任务，避免直接修改已经完成的 V3 主计划。当前 `.specify` 设置脚本会选择另一功能目录，因此本轮不运行会覆盖既有计划的完整 Spec Kit 生成流程。
