# V3-3 阶段验收：查询分析与多问题编排

日期：2026-09-28。**结论：V3-3 验收通过，停在本阶段；未进入 V3-4。**

## 交付内容

- 新增模型驱动的 `QueryAnalyzer`：简单独立问题直接检索；多意图、上下文指代和不清楚的问题使用本地模型生成并验证 `QueryAnalysis`，最多保留 3 个不同子问题。模型输出无效时回退到原问题，不臆造检索事实；即使模型误判，没有上下文的指代问题仍要求澄清。
- 生产 Ollama 路径中，证据为空或明确指向另一设备型号时，由模型提出一次不同的检索问题；离线 Fake 测试仍可使用旧规则生成器。自纠错有界，不会在同一子问题中反复搜索。
- 主图使用 [LangGraph `Send` Map-Reduce](https://docs.langchain.com/oss/python/langgraph/graph-api#send) 将最多 3 个子问题分发给独立 Agent；每个 Agent 保留原有 Child Search、必要的 Parent Store 读取、答案生成和自纠错；归并节点合并答案、检索证据、来源、执行轨迹，再执行一次原有答案评估。
- 同一请求内，规范化的重复子问题只运行一次；并行工具调用通过请求级单飞缓存避免相同 Query 或 Parent 重复访问底层检索器/Parent Store，请求结束即清理缓存。
- 澄清时不启动检索，保存待澄清原问题；用户在相同 `thread_id` 补充信息后，与原问题合并再进行查询分析和检索。这里使用已有 API 的“返回澄清、下轮继续”交互，不要求长时间挂起 HTTP 连接。
- `query_rewritten` 事件包含拆分问题；工具执行事件标注所属子问题；Query Analysis 和自纠错模型调用沿用 V3-2 的用量轨迹，不记录私有推理或提示词。

## 边界与后续

- 当前自纠错只处理“无结果”或“明确的设备型号冲突”；一般性的弱相关、证据冲突和数值事实核验属于 V3-4。
- 上下文压缩仍沿用旧的规则版；最终答案仍由各 Agent 分别生成后确定性拼合，不做 V3-4 的全局证据选择和最终综合生成。
