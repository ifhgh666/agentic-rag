# Feature Specification: P3 失效依赖清理

**Feature Branch**: 未创建或切换；当前检出 `codex/model-driven-agent-loop`。

**Created**: 2026-10-22

**Status**: P3 的 A/B 工程均已交付，20/20 工程任务完成、待用户验收；既有失败和正式数据未测范围保留，非全绿或真实质量验收。见 [B 阶段报告](phase-b-report.md)。

**Input**: P2 工程收尾报告后用户要求“继续”，承接架构改进路线的 P3 失效依赖清理；规格与技术规划先后交付，用户随后明确要求“执行”。前轮补齐任务清单并实施 A；用户随后要求“继续”，本轮实施 B，报告后暂停。P3 是架构路线阶段名，不是下面用户故事的优先级。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 维护者看到的问答依赖与实际执行一致 (Priority: P1)

维护者修改问答流程时，能从装配关系分辨真正参与执行的服务、策略和限制。正常问答不必构造仅为已停用路径准备的服务和缓存，也不继续传递没有接收者使用的内部参数。

**Why this priority**: 看似仍生效的依赖会误导修改和排障，也使新调用者承担已经失效的知识；本项应先于删除独立能力。

**Independent Test**: 对相同受控问答分别检查初始化与执行中的依赖使用，并比较清理前后的可观察结果和用量。未参与主图的旧服务不被默认构造或调用，当前策略和约束仍真实生效。

**Acceptance Scenarios**:

1. **Given** 某依赖只被构造和向下传递、没有参与当前主图决策，**When** 完成清理并执行正常问答，**Then** 主图不再默认构造它或为它分配专用缓存，也不恢复停用的业务路径。
2. **Given** 子流程装配接受一个实际未读取的内部参数，**When** 整理其调用关系，**Then** 不再形成虚假的内部依赖；同名设置若在真实执行位置仍生效，必须保留其作用。
3. **Given** 一个旧服务还被用于传递必要的设置或请求缓存，**When** 移除其无效业务装配，**Then** 必要依赖仍可明确取得，缓存隔离、共享预算和请求生命周期保持。
4. **Given** 单问、多分支、容量拒绝、修复或摘要场景，**When** 对比清理前后结果，**Then** 答案、来源、状态、原因、逻辑调用和历史处理保持原契约，不因清理增加模型决策。

---

### User Story 2 - 独立调用者保留已有能力与明确的兼容边界 (Priority: P1)

维护者和脚本调用者仍能使用已经对外提供的独立分析、改写、证据处理和答案生成能力。某能力未接入主图，不自动等于它不再受支持；不能为了主图清理删除仍在使用的模块或恢复旧语义策略。

**Why this priority**: 主图外仍存在真实代码调用，粗暴删除会把架构整理变成未经说明的能力移除。

**Independent Test**: 按受影响的独立调用清单执行受控调用，核对调用形状、结果结构及治理约束；兼容入口不导致主图额外构造或执行旧服务。

**Acceptance Scenarios**:

1. **Given** 某接口有独立脚本或工程用例调用，**When** 主图解除与它的失效关联，**Then** 独立能力及原返回形状保留，已有调用治理不被绕过。
2. **Given** 某兼容参数被接受但当前没有业务作用，**When** 维护其兼容入口，**Then** 明确记录其不生效的边界，不通过重新启用旧业务让它“生效”，也不静默将其解释为新的功能。
3. **Given** 文件同时包含旧策略与当前使用的来源转换能力，**When** 只清理失效依赖，**Then** 当前来源定位、序列化和引用仍正常工作，不能按整文件未使用处理。
4. **Given** 某条目的调用关系或兼容承诺尚不能确认，**When** 决定是否删除，**Then** 保留并记录待核对项，不把一次文本搜索无结果作为删除依据。

### Edge Cases

- 旧服务本体没有被调用，但设置、共享缓存等属性仍被读取；不能将整个实例直接判为无用。
- 参数名称与仍有效的全局设置相同；失效的是重复装配关系，不是预算、迭代或检索配置本身。
- 独立接口接受旧参数，测试或历史脚本仍传入；兼容形状与参数实际语义必须分别核对。
- 一份模块同时承担当前来源转换和旧证据筛选；不能按模块名或旧功能版本整份删除。
- 依赖仅出现在动态属性、类型注解或脚本中；静态无引用不能证明仓库外没有调用。
- 缓存命中、默认 fake 模式、失效租约、超时和可选摘要均可能绕过正常成功路径，不能只检查成功单问。
- 原工程失败及真实问答失败仍存在；清理不得删除失败断言、旧记录或改写质量结论来达标。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个拟清理条目必须有可审阅的使用证据、影响范围、当前用途和兼容判定；至少区分失效内部依赖、仍活动的依赖、独立保留能力及尚不能确认的条目。
- **FR-002**: 经核定失效的主图依赖不得继续被默认构造、创建专用资源或作为业务依赖逐层传递；不得为了保留装配而重新启用旧检索或旧证据策略。
- **FR-003**: 经核定无效的内部参数和传递关系应消除或明确隔离在兼容边界；仍有效的设置、真实执行限制和调用者能力必须保持，不得将同名参数一并误删。
- **FR-004**: 从旧依赖中仍需取得的设置、缓存或生命周期能力必须在清理后保持可用且归属明确；不得复制共享额度、丢失请求隔离或改变缓存计数。
- **FR-005**: 已列为保留的独立公开能力应保持原调用形状、返回结构和成功/失败行为；其中的模型调用继续遵守 P2 共同治理，不得通过删除接口规避验证。
- **FR-006**: 保留的无业务作用兼容参数必须有明确说明和验证；不新增静默语义、不自动恢复旧路径。拟移除有外部影响的接口或配置时，必须先在后续技术方案中给出清楚的兼容处理，不将本规格当作一揽子删除授权。
- **FR-007**: 保留当前问题分析、模型选择工具、有限修复、分支汇总、可选摘要及历史恢复行为；不得变更生产提示、结构约束、工具含义、聊天事件或对外用量字段含义。
- **FR-008**: 保持 P1 原文准入、Parent 实读范围、批次配对、缓存重检及部分交付；保持 P2 输入计量、共享预算、活动租约、单一截止时间、迟到隔离及诊断附属交付约束。默认模型 8/12 次、分支 5/4/3 次、请求最多 300 秒和单次默认 120 秒不扩大，原配置覆盖语义保留。
- **FR-009**: 任何代码或文件移除都必须有逐项证据和保留能力的验证，不删除历史首答、失败证据和阶段报告；不以改 prompt、删断言或扩大额度制造全绿。
- **FR-010**: 实施验证只使用 fake/scripted、假传输、受控时间和临时数据，并保留真实模型保护；没有另行授权，不访问正式知识库、索引或真实模型，也不以工程通过改判真实质量。
- **FR-011**: 范围限定为当前 RAG 装配中的失效关联及其必要局部整理、兼容核对和文档；不扩展为全仓格式化、依赖卸载/升级、目录再拆分、新抽象框架、功能恢复、前端改版或生产部署。
- **FR-012**: 最终交付必须对照清理前基线，列实际移除/保留/延期条目、真实运行命令和结果、当前架构关系及未测限制；原有失败继续单列，不把任务勾选当验收。

### Key Entities *(include if feature involves data)*

- **依赖条目**：待核对的服务装配、参数、状态传递或局部引用，带有定义位置、调用证据和影响范围；不是新的业务数据表。
- **兼容承诺**：保留的独立调用形状、返回结果和已存在行为，区分“接受参数”与“参数有业务作用”。
- **行为基线**：清理前可观察的答案、来源、状态、原因、调用统计、历史与诊断边界，供隔离工程对照使用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 最终清单中每个移除条目都有使用证据和结果映射，证据缺失条目被删除的数量为 0。
- **SC-002**: 经批准清理的失效依赖在正常问答中的默认构造、专用资源分配或旧业务调用次数均为 0；仍需保留的真实依赖有明确用途记录。
- **SC-003**: 对已选定的受控对照场景，答案、来源、状态、原因、逻辑调用次数和历史处理 100% 保持原约定；不比较不同请求 ID 或实测耗时的字节相等。
- **SC-004**: 保留清单中的独立调用契约检查全部保持，未经说明的外部接口/配置移除和恢复的旧业务路径数量为 0。
- **SC-005**: 原安全、容量、预算、期限、来源和诊断边界通过对应隔离检查；新增失败为 0，完整回归的既有失败和排除项目均如实列出，历史失败证据破坏数量为 0。
- **SC-006**: 交付报告逐项覆盖清理结论、证据、验证和限制；真实模型调用和正式数据修改数量为 0，未测真实质量明确标记未测。

## Assumptions

- 本轮“继续”承接原架构路线 P3；P2 已完成工程交付，不要求重新执行 P1/P2 或增设真实模型前置验收。本轮仍不宣称用户已经接受全部工程与质量结论。
- 起点是 P2 D 报告的 797 passed / 2 failed / 2 deselected，仅作历史基线，不是本轮成绩。两项旧提示词断言和 CURRENT_FAILURES 的真实失败继续保留。
- 默认保留仍有独立调用的旧能力；本次“失效依赖”首先指当前主图装配的无效关联，不等于允许删除所有旧版本代码或第三方依赖。
- 静态证据只能形成候选；具体参数、兼容方式、资源取得路径和实施阶段由后续技术规划决定。当前证据见 [scope-and-evidence.md](scope-and-evidence.md)。
- 规格、规划和 A 报告保持原文。用户在 A 报告后明确“继续”，本轮完成 B 的 procedure 清理、隔离后端及前端组合验证；最终后端为 802 passed / 2 failed / 24 skipped / 2 deselected，24 项依赖正式 PDF 的检查未运行，另两项真实嵌入检查排除。工程结论不改判真实问答质量。
