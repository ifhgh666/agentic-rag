# 研究与设计决定：模型驱动 Agent Loop

**日期**：2026-10-08。仅只读代码、文档和既有评测研究；未调用本地模型、未重跑问题。两项研究分别核对协议/循环架构和验收/成本，结论纳入本功能设计。

## R1：使用原生工具调用作为主方案

**决定**：完善现有ChatProvider，而非改用另一个Agent框架。每轮模型收到两个检索工具定义，输出工具请求或终态答案。结构化动作仅作为显式兼容协议，不能原生失败后偷偷退回规则。

**理由**：当前ModelResult已有tool_calls；OllamaProvider已有bind_tools；原项目也用绑定工具的模型逐轮invoke。缺口在多轮消息保真和编排接入。Ollama官方示例要求把assistant工具请求与tool结果放入后续消息，LangChain支持绑定工具；仅传(role, content)不足以保留调用关系。[Ollama工具调用](https://docs.ollama.com/capabilities/tool-calling)、[ChatOllama](https://docs.langchain.com/oss/python/integrations/chat/ollama)。

**替代方案**：继续Python规则不满足用户目标；另加“模型判是否调用模型”增加无用轮次；一次性重写所有框架扩大范围。结构化JSON动作依然可由模型决定，但与原生协议区分报告。

## R2：原生消息与多工具返回统一

**决定**：统一ToolCall(id/name/args)和消息(role/content/tool_calls/tool_call_id/name)，保留元数据；按ID合并所有工具返回。request_id由执行器注入，模型只能请求实际可用Parent。

**理由**：现有Ollama扁平化消息丢ID；兼容提供者的function.arguments可能为字符串，Ollama为args字典；执行器可执行多调用但状态仅看最后结果。无法配对时明确协议失败，不凭位置猜配对。

**替代方案**：只允许一个工具可以先简化，但不能让已有多调用被静默丢弃；完整列表摄取是必要修复，不是多Agent扩展。

## R3：循环终态由模型给出

**决定**：删除字数、非空、已取Parent、型号正则触发的下一步决策，以及固定两次搜索规则。预算/参数/引用真实性仍由程序检查；终态包含子答案或具体缺口。

**理由**：原项目[orchestrator](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/f0d9a3c89adc7ebd146ffe173057fe013dd41739/project/rag_agent/nodes.py#L173)每轮调用模型；工具结果回模型，模型不再请求工具时收集其答案。我们现有回边只是规则工具循环。模型正常终态与程序资源停止必须分开记录。

**替代方案**：模型只回答“够/不够”再由程序生成下一查询仍让程序承担重要语义；模型只停止检索后再额外生成虽可过渡，但不是本计划主方案。

## R4：保留原始证据，模型管理上下文

**决定**：原始候选尽量完整装载；超物理窗口时调用模型选择带原文/出处ID的证据、保留缺口。原始证据注册表不删除；消息压缩完整移除旧工具请求/返回对，不留下悬空消息。

**理由**：当前中文二字重合、截句和流程段落资格会替模型排除内容。压缩器不能改动数字和来源。上下文预算包含工具定义、系统提示、用户输入和输出预留，不能只算证据。LangGraph状态reducer会合并消息，列表赋值不一定真的删除历史。[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)。

**替代方案**：塞入全部资料会超窗；继续词面截取不满足语义决策目标；新增昂贵reranker本阶段非必要。

## R5：采用模型子答案，解除输出覆盖

**决定**：无工具调用时，content返回BranchAnswer结构；模型决定答案/不足，格式错误最多一次有限修正。单分支直接输出；多分支汇总答案和可追溯证据，保留引用定位。

**理由**：当前procedure模式丢模型答案、数字检查不区分题设，Loop即使正确也可能在输出时失败。25次生成中6次摘录路径，场景仅3.5/20。用户条件、文档事实、推导结论分开，不能靠标签宣称推导正确。引用核验仍不证明完整性。

**替代方案**：全删引用校验可能失去出处；保留原文覆盖仍损失结论；在线Judge多一层循环和成本，不在本阶段。

## R6：预算从2/4明确改成拟8/12

**决定**：单分支请求上限8，多分支12；分支编排上限5/4/3，预留汇总、共享一次压缩或格式修复；摘要只用余量。原子配额、公平分配、240秒请求截止及工具上限明示。

**理由**：真实循环至少需要问题理解、搜索决策、看到工具结果后的回答；多分支还要汇总。旧2次几乎不能运行新循环。旧批66次模型调用占约99.75%总时间，不能承诺更快。

**替代方案**：无限循环不可控；沿用2/4会频繁资源停止；为了缩短时间恢复规则违反目标。数字是拟定默认，阶段A实测后正式运行前冻结，不能看完评分再调整。

## R7：真实决定来源和同协议评测

**决定**：决策关联真实model_call_id；工具关联decision_id；cache和runtime_guard分栏。脚本提供者证明路由，真实冒烟证明本机协议，30题证明问答效果，三种不能互相代替。

**理由**：当前AIMessage可能由Python构造，SSE中的agent_decision也会由程序描述工具轨迹；不能仅换标签就称模型驱动。Q1/Q12理解失败、Q7/Q8/Q25澄清、六题生成失败要分层统计。基线无预算耗尽，不改写历史原因。

**替代方案**：只看总分会掩盖拒答和程序模拟；改变会话协议再比较会产生不公平提分；更多调用不能作为思考能力证据。
