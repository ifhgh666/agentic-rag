# C阶段补充：整次请求最多5分钟

日期：2026-10-09。授权范围：用户要求“设置这个最大的超时时间，最大为5分钟，超过直接判定为超时”。本次只调整超时及相关保护，没有启动D阶段或再次提交真实场景题。

## 当前方案

- `REQUEST_TIMEOUT_SECONDS=300`：从聊天API接收请求时开始计时，分析、各检索分支、生成、修正、压缩和摘要共用同一个绝对截止时间。新节点、流式进度和分支不会重置计时。
- 配置允许更短期限，拒绝0、负数及大于300秒的配置；API额外限制最大300秒。
- API使用独立的异步等待期限，即使同步步骤卡住，也在截止时返回`error(code=timeout)`和`complete(status=failed, reason=timeout, stop_origin=runtime_guard)`，记录实际耗时。
- 单次模型调用仍最多120秒，实际等待为`min(120秒, 请求剩余时间)`；检索工具也按请求剩余时间限制等待。单次调用提前到期同样判定timeout，不必等满5分钟。
- 超时结果不表示资料不足。迟到答案不发送给本次请求；会话提交前检查期限，若提交后摘要等步骤才到期，恢复本次请求前的会话状态。工具等待超时直接结束本轮，不再继续调用模型。

等待结束不等于强制杀掉Ollama已经开始的后台计算。当前保证的是平台请求停止等待、返回超时并隔离迟到结果；没有宣称已实现模型进程级强制终止。
