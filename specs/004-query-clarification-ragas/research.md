# 阶段 0 研究与决策

**日期**：2026-09-30。本文只确定设计方向，不代表已安装 RAGAS、已建标准答案集或已修改问答流程。

## 决策 1：每条新消息用一次结构化本地模型分析

**决定**：把“新题/澄清补充判断、指代消解、是否清晰、最多 3 个子问题”合并在一次模型分析中。该步骤默认覆盖每条新用户消息；格式校验和精确引文核验仍可用确定性代码。

**理由**：现有 `backend/app/rag/conversation_memory.py` 与 `query_analysis.py` 的正则语义分流对表述变化敏感；参考项目的 [`rewrite_query`](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/project/rag_agent/nodes.py) 使用结构化模型分析，能同时处理摘要、近期消息与待澄清内容。一次调用比“先分类再改写”更容易界定成本。

**比较过的替代方案**：继续累加正则特例（过拟合风险）；每条消息调用两个模型节点（调用成本更高）；完全照搬参考项目所有 Agent 调用（本机 4B 模型延迟和工具调用可靠性尚未证明）。

**执行约束**：普通简单题预期从 1 次生成调用增加为分析＋生成约 2 次；必须记录实际调用、Token、耗时及错误。模型失败不能伪装成功；原文检索只用于安全可解释的降级。模型摘要若会使请求超过当前简单题 2 次上限，应延后摘要或另行明确批准预算调整，不能暗增调用。

## 决策 2：待澄清状态与普通对话分离

**决定**：保留一个按 `thread_id` 访问的权威线程状态，显式记录 `pending_query`、补充列表、最近普通消息和摘要；新输入的关系为补充、新题或不确定。用户明确动作优先于模型判定。

**理由**：参考项目的 [`State`](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/project/rag_agent/graph_state.py) 已区分 `pendingQuery/pendingClarifications`，并用[主图检查点与中断](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/project/rag_agent/graph.py) 承接澄清。但它对下一条消息作为澄清仍有假设；我们补充换题、取消和不确定分支，避免现有“非空就拼接”。

**比较过的替代方案**：保留外部 `_threads` 字典与图状态两份待办（易分叉）；单靠消息 `role` 判断补充（不足以表达用户意图）；所有输入均强制追问确认（体验差）。

**执行约束**：首批仍使用进程内 checkpoint，重启丢失会话须明确显示；多进程持久化不在当前范围。应测试同线程并发，至少拒绝或串行处理重复请求，避免覆盖待办。

## 决策 3：摘要只在必要时生成，且不当作证据

**决定**：近期普通对话保留有限窗口；超出后对旧摘要和溢出轮次做增量概括。摘要用于后续问题理解，不进入最终答案的 PDF 证据列表。

**理由**：参考项目的 [`summarize_history`](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/project/rag_agent/nodes.py) 只在有溢出普通消息时调用模型。当前直接截取末尾字符可能丢失关键型号或未完成事项。

**比较过的替代方案**：每轮都摘要（成本过高）；只保留最近 4 条原文（长程指代丢失）；继续无语义字符截断（关键事实可能断裂）。

## 决策 4：标准答案先人工可核对，再做离线评估

**决定**：首批从现有 PDF 制作至少 15 个题目：Q1–Q5 正常题，加至少 10 个不同类别的变体与异常题。每题保存 PDF 指纹、来源页、引文原文、必答事实、禁止误答、预期拒答、人工核对状态。自动草拟可以辅助，但未经逐题核对的题目不能用于正式验收。

**理由**：参考项目的[评估 Notebook](https://github.com/GiovanniPasq/agentic-rag-for-dummies/blob/main/notebooks/evaluation.ipynb) 从精选问答集评估实际回答。题集若错误，Judge 分数再高也没有意义；Q3 的安全步骤尤其必须依原文逐项核对。

**比较过的替代方案**：只让回答模型自造题与标准答案（循环自证）；只用历史五题（覆盖面不足）；直接复制参考项目的题集（与本知识库事实不匹配）。

**执行约束**：无答案和澄清交互题须单列人工/确定性判定；不能把不适用的 RAGAS 指标强行记为 0。真实业务 PDF 尚未提供，首批题集只对现有测试 PDF 有效。

## 决策 5：RAGAS 作为独立离线实验，不是在线评分器

**决定**：对适用的已核对题目，离线运行与参考项目一致的五项指标：AnswerAccuracy、ContextRelevance、ResponseGroundedness、ContextPrecision、ContextRecall。输入记录必须包含标准答案、实际回答及实际检索/生成上下文；逐题保存分项原始分数、原因、模型版本与人工复核。对不适用的指标记录 `not_applicable` 与理由。

**理由**：[RAGAS 当前指标文档](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)区分答案、上下文和证据维度，也明确基于 LLM 的指标可能产生额外模型调用。参考项目使用独立 Judge 并在 Notebook 中批量运行，不在每个在线请求后运行。

**比较过的替代方案**：保留当前固定 84/100（误导）；每次在线问答都跑 Judge（本地延迟和成本大）；仅看单个总分（无法定位召回、生成或依据问题）。

**执行约束**：实现阶段先锁定与现有 Python 环境兼容的 RAGAS 版本及 Judge 适配方式，并做 1 题冒烟验证；计划阶段不擅自下载第二模型。若没有独立本地 Judge，允许先做题集/人工验收，或将同模型实验标为探索性，不宣称独立裁判。无云端评估调用。数值闸门应在题集核对和 Judge 稳定性校准后确定，不能事后为通过测试而选择。

## 决策 6：在线显示可验证状态，不显示未经证实的分数

**决定**：新增有版本标识的在线核验状态，区分证据、引文、数值和“未验证的完整性/事实正确性”。不再把 `backend/app/rag/evaluator.py` 的固定 90/78 作为可信度展示；前端改为事实状态说明。

**理由**：既有 [V3 验收](../003-v3-ollama-rag-quality/v3-post-acceptance-plan.md) 记录 Q3 漏掉安全步骤却仍获 84/100。能定位引文不等于答案完整。

**比较过的替代方案**：简单调高/调低固定分数（仍不真实）；在 UI 隐藏分数但继续向接口发送（下游仍可能误用）；用单次自评替换规则分数（同模型偏差及额外调用）。

## 已知风险与后续验证

- 本地 4B 模型的结构化输出稳定性、额外延迟和总调用预算，要用既有五题及新增样例实测；计划不预设可接受的模型性能。
- RAGAS 包版本与 Judge 模型能力是实施时的兼容性验证项；验证失败时保留人工题集与在线状态改造，不强行上线失真的自动评分。
- Q3 的答案生成/证据覆盖修复仍属既有 V3 后续计划；本功能的评估不能代替该修复。
