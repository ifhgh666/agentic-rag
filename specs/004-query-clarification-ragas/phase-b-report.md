## 阶段 4：实际行为与产物

- `ConversationMemory` 以经过验证的 `ThreadState` 保存唯一权威状态；原始待办、按时间排列的补充、已完成普通消息、语义摘要及未摘要原文分开。主图不再用跨轮 checkpoint 保存另一份待办；不根据 `message.role` 猜哪条消息是未完成任务，也不在 `prepare()` 用正则或字符串拼接决定补充关系。
- 默认由一次结构化模型分析判断关系；明确且完整的补充形成独立问题后检索。明确新题不混入旧待办；显式新题不向模型发送旧待办及旧补充。`continue_clarification/new_question` 动作优先于模型关系猜测；取消直接清除待办，模型调用为 0。不确定时保留原状态，显示继续补充／开始新问题／取消。
- 自动模式下，模型判为补充但仍不清楚时，增加通用状态保护：改为 `uncertain`，不把这条含糊消息写入补充；明确选择继续补充后才累计部分信息。这一保护只检查动作、结构化关系及清楚状态，不匹配具体词句、不增加模型调用；触发时记录 `decision_guard=unresolved_auto_supplement`。确定性型号／数值／否定范围校验仍只做保真检查，不负责语义路由。
- 每线程非阻塞请求锁返回 `THREAD_BUSY`；存储锁及递增版本防止并发覆盖，深拷贝防止调用方改写内部列表。不同线程隔离。分析失败不改变待办；已进入回答后若下游抛出异常，恢复原待办及历史，但版本继续递增。未知线程取消明确提示 `THREAD_NOT_FOUND`，不存在待办的显式补充提示 `NO_PENDING_QUERY`。
- API 已支持四种动作；普通问题必须非空且最多 2000 字符，取消必须带 `thread_id`、可以没有问题正文。新增版本 1 的 `analysis/clarification` SSE；澄清不发送普通答案、检索结果或旧评分事件。前端提供单独澄清卡和三种操作；失败保留卡片，到正常完成／取消才移除；新会话清空本地待办，并说明重启服务后会话失效。
- 新增 `conversation_summary.py`：仅在普通消息溢出时，使用旧摘要及已完成普通消息生成增量摘要，不带未完成待办、工具消息。摘要只作会话背景；必须保留型号、数值和限定条件，不把历史助手回答当作 PDF 事实。摘要失败或不保真时保留原文，不用字符截断替代语义压缩。

### 摘要预算与当前限制

简单请求总上限仍为 **2 次**、复杂请求为 **4 次**；摘要每请求最多 **1 次**，只使用剩余预算，不改用户实际 `.env` 或提高总调用上限。近期默认保留 4 条普通消息，摘要最多 2000 字符，溢出原文留在 `summary_backlog`。分析＋生成已用满 2 次时，摘要延后；后续有空余预算的请求可处理积压。

历史、摘要、待办和补充默认合计估算 4000 Token 的分析输入闸门；超限明确失败并建议新会话，不默默丢弃历史。这个保守策略意味着连续简单问答可能积压，**并不保证每轮都能压缩，也不保证长会话无限延续**。摘要只是模型生成背景且有字面保真检查，不宣称能自动证明其语义完全正确。会话仍只在进程内存中，持久化、多进程、完整重复请求幂等不在本阶段范围。
