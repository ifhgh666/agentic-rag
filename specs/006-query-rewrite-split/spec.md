## User Scenarios & Testing

### User Story 1 - 完整单问保留原文（Priority: P1）

用户提交清楚、完整的独立问题，系统判断可以检索后保留原句；不为改变表达而重新措辞。一次入口处理同时完成必要补全、拆分与清晰度判断。

**Why this priority**: 避免无益改写引入数字、型号或含义失真。
**Independent Test**: 六个完整单问逐字核对入口输出；记录调用数和真实结果，不能用预设答复证明模型保真。

**Acceptance Scenarios**:

1. **Given** 没有历史，**When** 用户问“PN8733 的启动电压是多少？”，**Then** 只输出原问题，不擅自纠错型号或回答电压。
2. **Given** 原题含内部空格、大小写、否定、小数或单位，**When** 问题本身完整，**Then** 保留这些文字，不把旧缓存的另一种写法当成本题结果。
3. **Given** 一项复杂需求包含共同条件，**When** 输入电压与持续时间共同决定一项判断，**Then** 不机械把电压、时长拆成两个不相干需求。

### User Story 2 - 必要补全与可控澄清（Priority: P1）

用户可以自然追问，系统只补充独立理解所需的上下文；对象无法确定时询问用户。待澄清原题与普通历史隔离，用户可以明确补充、换题或取消。

**Why this priority**: 解决“它”“那恢复条件呢”等问题，同时避免把新题混入旧待办。
**Independent Test**: 用固定历史、多个候选对象及显式动作验证补全和待办变化；这些是独立功能场景，不是失败后救分追问。

**Acceptance Scenarios**:

1. **Given** 历史唯一对象为 PN8733，**When** 问“它的恢复条件是什么？”，**Then** 补入 PN8733，不增加未确认事实。
2. **Given** 历史题设为 245 V 持续 400 ms，尚未确认是否触发保护，**When** 问“那恢复条件呢？”，**Then** 保留完整条件及“如果触发”的条件性。
3. **Given** 存在多个可能对象，**When** 问“它的参数是多少？”，**Then** 给出具体澄清问题且不执行检索。
4. **Given** 存在待办，**When** 明确选择继续补充，**Then** 合并原题和已确认补充；选择新题时不混入待办；取消时清除待办。
5. **Given** 存在待办但没有选择动作，**When** 提交自动消息，**Then** 请用户选择继续补充或开始新问题，不猜测消息关系，也不修改待办。

### User Story 3 - 按需求拆分并完整回答原题（Priority: P1）

真正独立的信息需求可以拆分；共享条件和依赖关系不能丢失。无论内部多少检索目标，用户收到一份覆盖原始请求的回答。

**Why this priority**: 既改善检索目标，也避免拆分后遗漏比较或条件性恢复。
**Independent Test**: 验证两问、三问、共同条件、条件恢复及比较；核对最终答案仍包含原题中的比较目标。

**Acceptance Scenarios**:

1. **Given** 两个或三个独立需求，**When** 处理问题，**Then** 最多三个检索目标且无遗漏、重复。
2. **Given** 问“245 V 持续 400 ms 是否触发保护，如果触发如何恢复？”，**When** 选择拆分，**Then** 两问均保留共同场景，恢复问不预设已经触发。
3. **Given** 比较 A/B 阈值并问哪个更高，**When** 分别检索 A/B，**Then** 最终回答仍完成比较，不机械增加第三路检索。
4. **Given** 四个以上独立需求，**When** 无法在三个目标中完整保留，**Then** 请用户选择本轮最多三项，不静默删除第四项。

### User Story 4 - 失败明确、过程可核对（Priority: P2）

用户能区分澄清、模型调用失败、格式失败、超时与资料不足。原题、模型输出、真实来源、调用数和耗时可追溯；公开信息不泄露完整提示词或私有推理。

**Why this priority**: 不能把取消拦截或流程运行成功当成回答质量修复。
**Independent Test**: 注入协议异常，检查终态、零检索、预算、会话回滚和事件来源；再单独做真实模型验收。

**Acceptance Scenarios**:

1. **Given** 模型失败、非结构化输出或空任务列表，**When** 入口结束，**Then** 明确失败，不自动重试、不假装使用原题完成改写。
2. **Given** 缓存命中、取消或待办动作待选择，**When** 没有入口模型调用，**Then** 记录真实来源，不伪造模型决策。
3. **Given** 请求达到 300 秒，**When** 后续仍有进度或迟到输出，**Then** 返回 timeout，期限不重置，迟到结果不写入正常历史。

### Edge Cases

- 明确但陌生的型号、缩写或文件名直接检索，不凭熟悉程度纠错。
- 单个需要补全的追问仍只输出一个问题；不能因为数量为一就强制换回原句。
- 模型输出四项属于容量/结构失败；用户输入超过三项时应获得具体容量澄清。
- 清楚却问题为空、问题重复、字段缺失/额外字段/类型错、清楚且有澄清文字，均为无效输出。
- 格式正确但数字或含义改错属于质量失败；V1不由入口新增语义节点阻断，测试必须如实发现和记录。
- 超时和下游失败恢复原待办；生成的子问题不能冒充用户原话进入普通历史。

## Requirements

### Functional Requirements

- **FR-001**: 一次有效、未缓存的入口处理最多使用一次模型调用，同时判断补全、拆分与清晰度；不增加前置分类或独立语义核验调用。
- **FR-002**: 结果只包含清晰度、问题列表和澄清文字。清楚时为 1–3 个非空、不重复问题且澄清为空；不清楚时问题为空且澄清具体非空。
- **FR-003**: 清楚完整单问保持当前用户原句；已有接口首尾空白清理除外，内部文字不得无意义归一化。
  - 2026-10-11 用户验收澄清：允许不影响题意的普通空格数量变化，RW03 双空格合为单空格可接受；不放宽型号、数字、单位、文件名、否定或条件保真。详见 [E 空格验收说明](phase-e-whitespace-acceptance-20261011.md)。入口 prompt 和运行时检查不因此修改。
- **FR-004**: 仅使用必要上下文解析指代、省略和确认补充；不添加答案、未知阈值、对象或未发生的保护结论。
- **FR-005**: 只有独立需求才拆分，最多三个；超过容量不静默截断。
- **FR-006**: 保留型号、数字、单位、文件/版本、时间、否定、比较、共同条件和条件依赖。
- **FR-007**: 原始请求始终保留到检索分支和最终回答；最终覆盖比较、恢复等全部目标，不简单拼接结果。
- **FR-008**: 不清楚时保存原题并请求具体澄清；存在待办而动作未明确时先请用户选择，不用程序分析文本来猜关系。
- **FR-009**: 继续补充、新题、取消动作分别生效；取消不调用模型，新题不混入旧待办，失败回滚原待办。
- **FR-010**: 普通历史保留真实用户输入及确认补充；改写文本只作为检索目标或独立诊断，不写成用户原话。
- **FR-011**: 保留基础协议、空值、容量和异常检查；拟撤去现有入口数字/型号来源不匹配的硬停止，不新增语义核验。已有摘要保真、引用定位和工具合法性继续有效。
- **FR-012**: V1入口自动重试为零；失败明确返回，不用未处理原题伪装成功，不自动切云。用户再次提交是独立新请求。
- **FR-013**: 缓存仅复用相同原题、线程、上下文、动作、索引和模型/策略版本的结果；原题内部空白和大小写不同不能误命中旧改写。
- **FR-014**: 复用现有记忆、检索与模型循环；检索工具、查询和继续决策仍由循环模型决定，不恢复程序语义规则。
- **FR-015**: 沿用调用/工具预算，整次请求最大 300 秒，不重置；单次模型等待同时服从现有上限和请求剩余时间。
- **FR-016**: 保留真实请求/调用关联、来源、澄清、失败、缓存、时间与用量记录；公共日志和事件不暴露密钥、完整提示词或私有推理。
- **FR-017**: 工程验证与真实补全/拆分/回答验收分开；保留首次输出和历史失败，一项顺序验收失败后保存记录并暂停。
  - 2026-10-11用户后续明确要求E遇错继续，按[继续规则](phase-e-continue-policy-20261011.md)运行剩余九题，失败保留且不重试；只改变E批次停止规则，不放宽质量标准或改变F停止规则。
- **FR-018**: 不重建正式知识库、不新增记忆存储、检索算法、模型下载或无关架构能力；每个实施阶段报告后暂停。

### Key Entities

- **原始请求**：用户原始消息及本轮明确动作，不被改写覆盖。
- **上下文与待办**：普通近期对话、摘要、未解决原题、已确认补充，来源分开。
- **补全拆分结果**：清晰度、最多三个问题、澄清内容。
- **分支与统一答案**：各检索目标、共享原始题设、证据和最终请求目标。
- **运行记录**：来源、请求/调用标识、原始输出、耗时和真实状态。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 固定六个完整单问在真实入口首次输出中 6/6 保留原文；任何数字/型号失真均不通过。
  - 原文保留按上述用户澄清核对内容；不影响题意的普通空格数量变化不单独判失败。旧批次报告保留原判定，本轮单列新验收依据。
- **SC-002**: 固定补全、模糊指代、显式澄清与动作案例均满足预期，无未确认事实或旧待办混入新题。
- **SC-003**: 固定拆分/比较/依赖/容量案例全部需求被保留，问题数不超过三，最终比较目标不丢失。
- **SC-004**: 异常、缓存、取消、隔离和期限工程检查全部通过；未缓存有效输入入口调用不超过一次，禁止隐藏重试。
- **SC-005**: 每个实际提交请求记录首次结果及耗时，终态在既有最大 300 秒等待边界内产生；mock期限与真实耗时分别报告。
- **SC-006**: 两道历史失败题的新补测结果单列、分别核对入口保真与完整回答；不以错误消失或引文匹配替代推导正确，不改写旧失败。
- **SC-007**: 规划与实施均保留正式数据和既有修改；每个获准阶段都有报告并停止，未运行项不标通过。

## Assumptions

- 源方案为设计依据；实施授权以用户逐阶段指令为准。2026-10-11 用户曾依次授权D/E/F，随后明确接受RW03普通空格变化并要求继续E。本轮仅续测E的未运行题，实质失真仍停止；F和005不会自动恢复。
- 三字段不再表达旧关系分类。已实施的待办状态下自动消息先选择动作；兼容关系字段来自程序动作适配。
- A 阶段已取消入口数字硬拦截；提示词与工程测试不能保证模型永不改错。严重保真错误必须阻止真实验收通过。
- 暂沿用独立子分支、单分支直接答案、多分支模型汇总；不创建依赖图或统一重写Loop。
- 保持已配置本地模型与预算；旧README中2/4次调用是历史快照，以本轮非敏感配置读取的8/12为规划基线。
- 005 C真实验收仍未通过，T018未完成、D未启动。006的计划及补测不自动恢复005或启动30题正式评测。
