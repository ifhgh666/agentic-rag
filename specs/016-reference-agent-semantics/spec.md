## User Scenarios & Testing

**E 全量测试授权（2026-10-28）**：用户明确要求全测、前题失败不影响后题、最终比较模型答案与正确答案。本阶段按 [E 协议](phase-e-full-gold-20261028-protocol.md)新批次运行 gold-1.0 全 15 场景/19 轮，替代 D 的失败停止规则；只测试和分析，不修改产品或标准答案，报告后暂停。旧 D 首答失败保留，不与新批次择优拼接。

**E 结果**：15 场景/19 轮全部采集，11通过/4部分正确未通过/0未运行；10 独立事实题的36个必答要点全覆盖，但 Q3/Q15 附加“自检资料未说明”、Q14 无效数值推断，以及 Q9 恢复流程/附加断言导致完整答复未通过。见 [全部原答对照](phase-e-answer-comparison-20261028.md)和 [E 报告](phase-e-full-gold-20261028-report.md)。行为8轮符合不等于最终答案全正确；报告后暂停。

### User Story 1 - 按参考研究流程回答 (Priority: P1)
用户提问后整理历史、分析、并行研究、按需压缩、统一聚合。维护者能直接从图理解模型与工具往返。
**Why this priority**: 用户拒绝只调整目录而保留旧算法。
**Independent Test**: 固定参考与相同scripted模型/工具的消息、节点、次数、上下文和输出对照。
**Acceptance Scenarios**:
1. 单问也聚合；三个子问独立研究并按序汇总；新一轮不累积旧答案。
2. 无工具请求直接collect，不强制BranchAnswer、引用修复或先有检索。
3. 本批工具越过研究上限后模型fallback；迭代边界仍允许无工具的最终回答。
4. 超阈值后模型压缩，保留检索标识并清理旧工具消息后继续。
5. Parent返回完整已存章节，不要求先搜索或翻页。

### User Story 2 - 自然澄清和真实过程展示 (Priority: P2)
用户直接补充待澄清问题，也可新题/取消；一份线程状态保存历史和待办。界面展示实际执行事件，只把聚合输出作为答案。
**Independent Test**: 隔离API/SSE与前端契约检查。
**Acceptance Scenarios**:
1. pending时auto/continue均恢复；new/cancel清理pending并保留已完成历史和摘要；cancel无模型调用。
2. 同线程并发拒绝，跨线程隔离；无总调用硬限或虚假分母。
3. 不生成在线核验卡，不以来源存在宣称语义正确。
4. 补充待澄清问题时若入口传输失败，保留原 pending 并释放线程互斥；普通问题执行失败不能被当成新的澄清待办。

### Edge Cases
连续澄清、重复工具、空检索、未知但有效Parent、模型异常、递归上限、Sources文件名不存在、压缩后来源保留、连接断开、旧会话不混入新图。

## Requirements

### Functional Requirements
- **FR-001**: 恢复参考主图/研究子图/消息reducer/两类摘要/澄清和聚合语义。
- **FR-002**: 参考原始提示、入口三字段；不加旧联动schema、代词兜底或业务重试。
- **FR-003**: 每分支8工具请求/10迭代、递归50、近期消息4、压缩2000/0.9；取消本项目300/120秒、8/12总调用、5/4/3配额、3072准入、768输出限制。
- **FR-004**: 工具参考字符串+完整Parent；真实artifact元数据仅供来源/界面，不添加模型决策。
- **FR-005**: 当前模型/端点/密钥和知识索引保持，使用已有SDK原生工具，不自动切换provider。
- **FR-006**: checkpoint是在线会话事实来源，支持默认续答/new/cancel和互斥。
- **FR-007**: 原聊天入口交付实时图事件/累计最终答案；移除verification；用量仅统计，model_call_limit=null。
- **FR-008**: 来源是最终Sources与本次真实工具元数据的交集；公开事件过滤提示、私有推理、密钥和敏感异常。
- **FR-009**: 独立旧接口及冻结依赖保留legacy侧；正常入口无旧治理栈和旧主图回退。
- **FR-010**: 保存原基线、测试迁移及质量失败；A工程结果不能冒充B真实质量。
- **FR-011**: A报告后暂停；不重启、不重建正式索引、不提交推送、不运行B。

### 约束解释与验收边界

- FR-002 的生成模型为 `is_clear: bool`、`questions: list[str]`、`clarification_needed: str`，三个字段均必填，允许空列表和空字符串。保持参考 Pydantic 默认解析，不新增 strict、`extra=forbid`、anyOf、列表截断或清楚状态必须清空澄清文字的联动校验。最多三问是原始提示要求，A 对照记录其行为，B 才验证真实模型是否遵守。
- FR-003 计数包含 orchestrator 本次返回的工具请求。先判断无工具直接 collect；有工具且 `iteration_count >= 10` 或 `tool_call_count > 8` 时整批不执行，改走模型 fallback。摘要、压缩、fallback 和聚合调用不属于这两个计数；递归 50 是图步数配置。
- 压缩在工具执行后按 `tokens(messages) + tokens(summary) > 2000 + int(tokens(summary) * 0.9)` 触发；等于阈值不压缩。这是研究状态整理，不是旧的输入准入硬限制。
- FR-005 保持当前 provider 配置。兼容端点入口显式使用 `function_calling`，Ollama 入口保留参考节点的无 method 调用，沿用已安装 SDK 默认；研究节点均使用 `bind_tools`。不把统一协议作为新增要求。
- 取消旧 300/120 秒应用截止不构成新的墙钟上限承诺；SDK/服务传输仍可能失败或长期等待。A 只核对参数和模拟行为，B 单独验证真实服务兼容性。
- FR-006 中 new 的清理动作不调用模型，随后处理新问题仍会调用模型；cancel 整个动作无模型调用。HTTP 请求校验和图内错误的区别见 [聊天契约](contracts/chat.md)。
- FR-008 的来源匹配、字段白名单和错误映射在聊天契约中定义；检索正文是获准界面展示内容，提示正文和研究摘要不因此成为公开字段。
- SC-001–004 的工程门槛、历史失败例外和阶段报告要求见 [计划](plan.md)及 [验证指南](quickstart.md)。全量 pytest 非零退出必须如实记录，不写成全部通过。

### Key Entities
聊天消息/摘要/pending及补充；分支消息/研究摘要/检索标识/有序答案；真实工具出处；只观测的事件和用量。

## Success Criteria
### Measurable Outcomes
- **SC-001**: 受控对照场景的消息、节点、调用和输出与固定参考一致，适配差异逐项记录。
- **SC-002**: 单问、并行、澄清、压缩、收尾、来源和流式契约检查通过。
- **SC-003**: 原数据和历史失败不变，公开敏感信息泄露为零。
- **SC-004**: A真实模型调用/正式数据操作/服务重启/提交推送为零，B保持未执行。

## Assumptions
用户最新批准明确替代005/006/007/010/011/015中冲突的在线限制，历史文档不重写。原文提示不保证中文输出。保留底层检索算法；SDK/服务传输错误仍可能发生。
